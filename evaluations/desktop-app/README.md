# Evaluation: desktop app, 2026-11-09

This compares a plain prompt with each generated agent on the same uncommitted change in a real repository. Sections 1–6 cover the first run, with `code-reviewer` 1.1.0 and `tester` 1.0.0. Section 7 re-runs the agents after the fixes, with `code-reviewer` 1.2.0 and `tester` 1.1.0.

## 1. Setup

### 1.1 Repository

The target was a private Electron 44 desktop app with a React 19 and antd 5 renderer, a SQLite main process, and Jest 30 with React Testing Library. It is hosted on GitLab, merge requests go into `dev`, and it has a detailed `CLAUDE.md`. The project is private, so this report quotes only the dummy code written for the test.

### 1.2 The dummy change

A small "project search and duplicate" feature plus a file-size formatter: 7 files, +61/−2, written in the repository's style. It passes ESLint and Prettier, so every problem is a logic problem, not a style one. Eleven flaws were seeded, including two that are deliberately ambiguous, to test whether an agent asks instead of guessing.

| #   | Where                | Seeded flaw                                                                            |
| --- | -------------------- | -------------------------------------------------------------------------------------- |
| 1   | `searchProjects`     | SQL built by interpolation, `LIKE '%${query}%'`: injection, and a `'` breaks the query |
| 2   | `projects:duplicate` | `catch` logs and swallows the error, so the channel reports success with no data       |
| 3   | `projects:duplicate` | No user-facing error for a missing project                                                   |
| 4   | `projects:duplicate` | Skips `validateName`, the project folder and the manifest that `createProject` creates |
| 5   | `projects:duplicate` | `console.log` in the main process                                                      |
| 6   | `projects:duplicate` | **Ambiguous:** documents are not copied. Is that intended?                             |
| 7   | `formatFileSize`     | `size > 1024`, so 1024 shows as "1024.0 B"                                             |
| 8   | `formatFileSize`     | `unit < units.length` steps past "GB", giving "2.0 undefined"                          |
| 9   | `formatFileSize`     | Negative, `NaN` and `undefined` input are not handled                                  |
| 10  | `formatFileSize`     | **Ambiguous:** decimals on bytes ("512.0 B"), and whether KB is 1000 or 1024           |
| 11  | everything           | No tests                                                                               |

### 1.3 Method

Each run used its own temporary git worktree of the repository with the same uncommitted patch applied, so the runs could not affect one another or the real working tree. Every run was a fresh subagent with the same model. The plain runs got only the repository path and the prompt. The agent runs got the generated agent file as their instructions, plus the same path and prompt.

| Run          | Prompt                                       |
| ------------ | -------------------------------------------- |
| Plain review | "Review the uncommitted changes"             |
| Agent review | the same, with the generated `code-reviewer` |
| Plain tests  | "Generate tests for uncommited changes"      |
| Agent tests  | the same, with the generated `tester`        |

Both agents were generated by running each kit's `SKILL.md` as written against a clean worktree. Subagents cannot interview, so every interview question was answered "defaults".

## 2. Generating the agents

|                | code-reviewer                                                           | tester                                                                                        |
| -------------- | ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Body length    | 150 lines (first draft 159, trimmed)                                    | 115 lines                                                                                     |
| Phase 5 checks | pass, after fixes                                                       | pass                                                                                          |

Both generators found real, repository-specific conventions. Examples: a dedicated error class for user-facing messages, an in-memory database helper because the native SQLite driver cannot load in Jest, "never extend the legacy synchronous IPC switch", and not re-reporting the known bugs listed in `CLAUDE.md`. They also turned the generic default rules into rules that fit the repository. Neither banned `console.log` in `electron/`, where electron-log captures it on purpose. Neither banned `container.querySelector('input[type="file"]')`, which the existing upload tests rely on.

### 3.2 Beyond the seeded flaws

Both reviews also found that `%` and `_` act as wildcards, that the sort order has no tie-break unlike `listProjects`, and that the IPC contract in `CLAUDE.md` was not updated. Only the plain review noticed that duplicating twice gives two projects with the same name, and that the renderer already filters projects on the client, so the server-side search may not be needed.

### 3.3 How they worked

|                    | Plain                            | Agent                                                                                |
| ------------------ | -------------------------------- | ------------------------------------------------------------------------------------ |
| Ran lint and tests | no                               | yes: lint ✅, tests ✅ (80 suites, 374 tests)                                        |
| Structure          | three ad hoc groups              | 2.6 severities, Open questions, verdict                                              |
| Verdict            | none                             | REQUEST CHANGES                                                                      |
| Ambiguity          | stated as a defect or an "if"    | moved to Open questions                                                              |

| Cost               | 54.5k tokens, 5 tool calls, 33 s | 54.0k tokens, 10 tool calls, 76 s                                                    |

### 3.4 Verdict

On this change the plain prompt was as good as the agent, and slightly better at finding problems. The model already finds this kind of flaw well, and the test repository's `CLAUDE.md` gives the plain prompt most of the context the agent was built from. The agent's value here was consistency: it ran the project's checks, used a fixed severity scale, gave a verdict and kept open questions separate. It also has a cost: its 150-line limit and checklist seem to narrow its attention. It skipped two input-handling issues that the plain review found by reading freely.

### 4.2 Verdict

The agent was clearly better here. The plain run wrote more tests, but it left the suite red, and it asserted a guess about ambiguous behaviour. A future fix that makes "duplicate" copy the documents would break that test, which is exactly the "test locks in a guess" problem from 4.5. The agent left a green suite, gave the bug-exposing tests to the user to add once the bugs are fixed, and asked about every ambiguity the plain run guessed at.

Two weaknesses showed up:

1. **The proof was weak for new code.** All 12 new tests "failed on the base commit" only because the functions don't exist there. That proves nothing about their assertions. For new code, the check should change the implementation instead (for example, invert a condition) or be reported as "not applicable".
2. **Severity drift.** The tester rated SQL injection MAJOR, but 2.6 defines a security issue as a BLOCKER. The reviewer got this right.

## 5. Changes this suggests for the kits

All 18 were applied in code-reviewer 1.2.0 and tester 1.1.0. They have not been re-evaluated yet.

Both generator runs reported problems with the skills, and the runs above add more. Proposed fixes, by kit:

**Both kits**

1. Host awareness: the fixed `gh pr diff` and "pull request" wording assumes GitHub. Detect the host from the remote; on GitLab, use `glab mr diff` or plain git, and the word "merge request".
2. Base branch: when `origin/HEAD` is not set, check the docs (`CLAUDE.md`, README), the CI config and recent merge targets before treating it as unclear.
3. The placeholder check flags real path notation such as `files/<projectId>/...`. Allow it in backticks, or prescribe `{projectId}`.
4. Before proposing a default banned pattern, search the existing code for it; drop the ban or add an exception when the project relies on it.
5. Mark values as "detected" or "inferred" in the Phase 3 summary.
6. Add a "known issues" slot, so documented bugs (here, a known-bugs section in `CLAUDE.md`) are not re-reported.

**code-reviewer**

7. With many focus areas, the 150-line limit forces cuts. Either give fewer, sharper checklists, or allow more lines when more areas are selected.
8. A "Type safety" variant for plain JavaScript with JSDoc.
9. A rule for when the only test command runs the full suite: fast or slow, or run only the affected specs.
10. Require `file:line` from `git diff` line numbers. The agent cited function names instead.
11. Keep a short "anything else you notice" step after the checklist. The plain review's extra findings came from reading freely.

**tester**

12. Turn off forced coverage for single-file and proof runs (`--coverage=false` when `collectCoverage` is on).
13. Proof for new code: a test failing because the function doesn't exist is not proof. Use a mutation check, or report it as not applicable.
14. In the proof step, use `git rev-parse --show-toplevel` instead of `$PWD`.
15. Flag a conflict between the mocking default and existing practice during discovery. The repository's service tests mock sibling modules.
16. Allow naming and location rules per area (`*.spec.js` in `src/`, `*.test.js` in `electron/`).
17. An optional lint step for new test files, when CI lints tests.
18. Restate the 2.6 severity mapping in the template, so security bugs are BLOCKERs.

## 6. Bottom line (first run)

- **code-reviewer:** about the same quality as a plain prompt on a well-documented repository. Its value is consistency: the checks run, severities are stable, there is a verdict, and open questions are kept apart. It needs the fixes above so its focus doesn't cost findings.
- **tester:** clearly better than a plain prompt. It left the suite green, didn't lock in guesses, proved its tests, and asked about ambiguities.
- **Generation:** about 190k tokens in total, once per repository. Both agents picked up real conventions of the repository that a plain prompt only gets when `CLAUDE.md` is this thorough.

## 7. Re-run with code-reviewer 1.2.0 and tester 1.1.0

### 7.1 Method

Both agents were regenerated with the new skill versions, from the same clean worktree, with the same "defaults" answers. They then ran on fresh worktrees with the same dummy patch and the same prompts as in 1.3. The plain-prompt runs were not repeated, because they don't depend on the kits; sections 3 and 4 hold their results. Every run is a single sample, so some of the difference between runs is noise.

### 7.2 Generation

| | code-reviewer 1.1.0 → 1.2.0 | tester 1.0.0 → 1.1.0 |
|---|---|---|
| Body length | 159, trimmed to 150 → **145, no trimming** | 115 → 113 |
| Base branch | `dev`, chosen without citing a source → `dev` from `CLAUDE.md` and 46 of 48 merges | same |
| Test command | full `npm test` → `npx jest --findRelatedTests` with coverage and the junit reporter off | single-file and proof commands now turn coverage off |
| Inferred values | not marked → marked `(inferred)` | same |
| Known issues | handled with an ad hoc note → detected (the known-bugs section of `CLAUDE.md`) | detected; never asserted |
| Banned patterns | defaults → searched first; scoped to `src/`, constant SQL fragments allowed | searched first; `container.querySelector` and `fireEvent` allowed for file inputs |
| Mocking | n/a | boundaries only, against the code's practice → **follow existing tests** (24 files mock collaborators) |
| Cost | 98.7k → 97.4k tokens | 90.1k → 93.5k tokens |

### 7.3 Code review

| | Plain | Agent 1.1.0 | Agent 1.2.0 |
|---|---|---|---|
| Seeded flaws found | 11 / 11 | 9 / 11 | **11 / 11** |
| Bad input (#9) and byte decimals (#10) | ✅ | ❌ | ✅ |
| Duplicates the client-side search | ✅ | ❌ | ✅, with the exact differences (case, trimming) |
| `file:line` on every finding | partly | no (function names) | **yes; all line numbers checked and correct** |

| Cost | 54.5k, 33 s | 54.0k, 76 s | 54.4k, 66 s |

The second read without the checklist (fix 11) and `path:line` from the diff (fix 10) closed the gaps from section 3.4. The agent now matches the plain prompt on findings, at the same token cost, while keeping its consistency: checks run, fixed severities, a verdict, and open questions kept apart. The only finding the plain review had that 1.2.0 did not was the duplicate-name collision ("X (copy)" twice).

### 7.4 Tests

| | Plain | Agent 1.0.0 | Agent 1.1.0 |
|---|---|---|---|
| Tests added | 36 (9 failing) | 12 | 8 |
| Suite afterwards | red | green | green (80 suites, 382 tests) |
| Locked-in guesses | documents, wildcards | none | none |
| Proof | none | 12 "failed on base" only because the code was missing (meaningless) | **8 failed under real mutations** (wrong channel, `toFixed(0)`, ÷1000, `ASC`, missing `%`, dropped " (copy)") |
| Bug severities | n/a | injection MAJOR | injection and swallowed error BLOCKER; size bugs MAJOR |
| Ambiguities asked | none | documents, validation, decimals, case | documents, error message, wildcards, tie-break order |
| Line references | n/a | function names | one `file:line`, and it was wrong (`format.js:20`, the loop is on 23) |
| Cost | 57.7k, 60 s | 66.1k, 128 s | 67.0k, 141 s |

The mutation proof (fix 13) works: every new test is now shown to catch a real change in behaviour, not just a missing function. Severity drift is only partly fixed. The template defines any bug as a BLOCKER, but the agent still rated the `formatFileSize` bugs MAJOR. It also stopped asking about bad input (`undefined`, `NaN`, negative numbers) and skipped validation, which 1.0.0 raised. That may be run-to-run noise.

### 7.5 Remaining fixes

The re-run and both generators point to these next changes. All 10 were applied in code-reviewer 1.3.0 and tester 1.2.0; they have not been re-evaluated yet. Fix 2 refined the shared severity definition in 2.6, since both agents rated the size bugs MAJOR in both runs.

1. **Line numbers in the tester:** require `path:line` from `grep -n`, as the reviewer does; its one line reference was wrong.
2. **Severity in the tester:** spell out that every confirmed bug is at least a BLOCKER per the definition, or relax the definition to separate crashes and security issues from wrong formatting.
3. **Related-test commands must not write files:** turn off coverage and file reporters (here jest-junit into `artifacts/`) for a read-only reviewer, and count runner CLI flags of an installed dependency as existing commands.
4. **Tool availability:** check that `gh` or `glab` is installed, and fall back to plain git when it isn't.
5. **Real JSX vs placeholders:** the `<...>` check flags real code such as `<AppContext.Provider>`; exempt code that exists in the repo.
6. **Base branch from CI:** CI disagrees with the docs only when it names a different merge request target, not when it also runs on `main`.
7. **Focus areas for desktop apps:** Electron or IPC security (`nodeIntegration`, `contextIsolation`, the renderer as a trust boundary, shell exec) fits no option, and needs a slot for the project's security model.
8. **Irrelevant defaults:** drop default bans and interview options that don't apply (no network layer, no coverage threshold, no slow suites).
9. **Ignored paths:** also read the linter ignore list and `.gitignore`, and include fixture and runtime-data folders.
10. **Hooks:** read `.husky/` and lint-staged configs during discovery.

### 7.6 Bottom line

- **code-reviewer 1.2.0** now finds as much as a plain prompt (11/11), with correct line numbers, at the same cost, and adds checks, stable severities, a verdict and separate open questions. It is worth using over a plain prompt.
- **tester 1.1.0** keeps the lead from the first run, and its proof is now real. Its remaining weaknesses are line references and severity.
